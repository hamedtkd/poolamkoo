# Data safety model

پولم‌کو Local-First است؛ این یعنی داده مالی اصلی داخل IndexedDB همان Origin نگه داشته می‌شود، نه روی سرور مرکزی.

## سه لایه حفاظت

1. **IndexedDB اصلی** برای کار روزمره.
2. **Recovery Snapshot محلی** برای برگشت از حذف یا Restore اشتباه. این Snapshot در همان Browser Storage است و در برابر پاک‌شدن Site Data یا خرابی دستگاه محافظت نمی‌کند.
3. **Backup فایل** برای نسخه مستقل از مرورگر. برای استفاده جدی، نسخه رمزنگاری‌شده را در فضای دیگری مثل دیسک دوم یا فضای ابری شخصی نگه دارید.

## یادآوری Backup

بعد از حداقل ۲۴ ساعت استفاده معنادار، اگر بکاپی ثبت نشده باشد اپ پیشنهاد بکاپ می‌دهد. بعد از بکاپ، اگر ۷ روز بگذرد دوباره یادآوری فعال می‌شود. کاربر می‌تواند آن را ۳ روز Snooze کند.

## Recovery history

حداکثر ۵ Snapshot جدید نگه داشته می‌شود. Snapshot خودکار حداکثر روزی یک بار ساخته می‌شود و عملیات تخریبی مهم نیز قبل از اجرا Recovery Point می‌سازند.

## Restore

قبل از جایگزینی داده با Backup فایل یا Recovery Snapshot، وضعیت فعلی محلی ذخیره می‌شود. Import فقط جدول‌های داده اصلی را جایگزین می‌کند و متادیتای دستگاه و Recovery history را پاک نمی‌کند.

## محدودیت صادقانه

Browser Storage بکاپ دائمی نیست. حتی اگر مرورگر Persistent Storage را تأیید کند، کاربر یا سیستم همچنان می‌تواند Site Data را پاک کند. تنها Backup خارج از همان Browser Profile یک نسخه مستقل محسوب می‌شود.

## Update و چند تب

از v0.20 اگر نسخه جدید Poolamkoo نیاز به بازکردن ساختار جدید IndexedDB داشته باشد، تب قدیمی اجازه ندارد بی‌صدا با اتصال قبلی به نوشتن ادامه دهد. رویدادهای `blocked` و `versionchange` به UI منتقل می‌شوند؛ تب قدیمی اتصال Dexie را می‌بندد و کاربر برای Reload امن راهنمایی می‌شود. Live Queryهای مالی نیز تا پایان Bootstrap دیتابیس شروع نمی‌شوند.

این مکانیزم Backup نیست و داده را جابه‌جا یا پاک نمی‌کند؛ فقط ریسک هم‌زمانی بین نسخه قدیمی و جدید اپ روی همان Origin را کاهش می‌دهد.

## بکاپ قابل‌راستی‌آزمایی در v0.21

فایل‌های بکاپ جدید از Envelope نسخه ۲ استفاده می‌کنند. این Envelope علاوه بر زمان خروجی، وضعیت رمزنگاری، نسخه برنامه و نسخه ساختار دیتابیس، یک SHA-256 digest از Metadata نسخه ۲ و Payload ذخیره می‌کند تا خرابی یا ناقص‌شدن فایل قبل از Restore تشخیص داده شود. برای بکاپ رمزدار، AES-GCM همچنان لایه احراز اصالت رمزنگاری‌شده است؛ SHA-256 اینجا برای تشخیص خرابی فایل است و جای امضای دیجیتال را نمی‌گیرد.

قبل از جایگزینی داده، پولم‌کو اکنون این مراحل را انجام می‌دهد:

1. Envelope و تاریخ خروجی را بررسی می‌کند.
2. اگر فایل رمزدار باشد آن را با رمز کاربر باز می‌کند.
3. digest فایل v2 را بررسی می‌کند.
4. نسخه Schema را با نسخه Local Database فعلی مقایسه می‌کند.
5. جدول‌های ضروری و Settings را اعتبارسنجی می‌کند.
6. تعداد پول‌های ورودی، صندوق‌ها، دارایی‌ها و تراکنش‌ها را به‌صورت Preview نشان می‌دهد.
7. فقط بعد از تأیید کاربر یک Recovery Snapshot از وضعیت فعلی می‌سازد و Import را شروع می‌کند.

بکاپ‌های قدیمی v1 همچنان قابل خواندن‌اند و به‌عنوان Legacy شناخته می‌شوند. اما اگر فایل یا Snapshot با Schema جدیدتری از نسخه نصب‌شده ساخته شده باشد، Import قبل از هر Clear/Replace متوقف می‌شود و کاربر باید ابتدا خود برنامه را به‌روزرسانی کند.

Recovery Snapshotهای جدید نیز `schemaVersion` و `appVersion` دارند. Snapshotهای قدیمی بدون این Metadata حذف یا بی‌اعتبار نمی‌شوند و همچنان با Validation معمول به‌عنوان Legacy بررسی می‌شوند.

## خروجی گزارش در v0.29

خروجی Reports با Backup فرق دارد و برای انتقال کامل دیتابیس طراحی نشده است. دو سطح آگاهانه وجود دارد:

- **خلاصه اشتراک:** فقط درصدها و وضعیت تصمیمی را می‌سازد و مبلغ‌ها و نام دارایی‌ها را عمداً حذف می‌کند. این متن فقط پس از اقدام صریح کاربر به Clipboard یا Share Sheet سیستم‌عامل تحویل داده می‌شود.
- **CSV کامل:** فایل محلی شامل جزئیات همان گزارش، از جمله مبلغ‌ها و نام/ارزش دارایی‌هاست. این گزینه برای نگه‌داری/تحلیل شخصی است و تراکنش خام، Backup payload، Recovery Snapshot یا Metadata دستگاه را Export نمی‌کند.

Poolamkoo برای این قابلیت لینک اشتراک میزبانی‌شده، Upload خودکار یا دیتابیس گزارش سروری اضافه نمی‌کند. نام‌های متنی قبل از CSV در برابر Spreadsheet formula prefixهای خطرناک خنثی می‌شوند.
