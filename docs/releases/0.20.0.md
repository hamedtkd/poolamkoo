# v0.20.0 — Safe app updates and local database upgrades

This release focuses on upgrade reliability before adding another financial feature. It keeps PWA updates and multi-tab IndexedDB schema changes explicit, recoverable, and non-destructive.

## PWA update lifecycle

- A newly installed Service Worker no longer calls `skipWaiting()` unconditionally during `install`.
- When an existing installation receives a new Worker, the Worker remains in `waiting` until the user accepts the in-app update notice.
- Accepting the update sends `SKIP_WAITING`; the page reloads only after `controllerchange` confirms the new Worker has taken control.
- Dismissing the notice keeps the current session running on the existing Worker.
- The app asks the registration to check for updates again when the tab regains focus/visibility.
- Service Worker cache version is `poolamkoo-v36`.

This avoids switching application shells in the middle of an active financial session and reduces the chance of old/new release assets being mixed.

## IndexedDB multi-tab protection

- Dexie now listens for `blocked` and `versionchange` lifecycle events.
- A stale tab closes its database connection when another tab upgrades the schema instead of continuing to write through an old connection.
- A blocked upgrade shows a specific Persian recovery message telling the user to close/refresh other Poolamkoo tabs.
- A stale/outdated tab asks for a safe reload rather than repeatedly retrying an incompatible local schema.
- Financial `useLiveQuery` subscriptions start only after database bootstrap succeeds, so reads do not race the initial open/upgrade path.
- Retry explicitly reopens Dexie after a failed bootstrap.

## Data-safety boundary

- No database reset, delete, or origin migration is introduced.
- Existing IndexedDB data remains attached to the same `poolyar-local` database on the same origin.
- No error path recommends clearing Site Data as the first action.
- Background Push remains paused and no new server infrastructure is required.

## QA focus

Release verification should include a real two-tab IndexedDB upgrade scenario and a deployed PWA update from the previous release, in addition to the normal `npm run check` and `npm run build` gates.
