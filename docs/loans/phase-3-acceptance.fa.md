# گزارش پذیرش Phase 3: Loan Product UI

> وضعیت: Complete
>
> این فاز هسته Loan Core فاز 2 را به یک مسیر کامل محصولی در Workspace تبدیل می‌کند. موتور اعلان زمان‌دار و پایش خودکار ریسک عمداً برای Phase 4 باقی مانده است.

## خروجی محصول

- مسیر `/loans` برای مرور همه وام‌ها، مانده بدهی، قسط بعدی، پوشش ذخیره و وضعیت نیازمند توجه.
- Wizard چهارمرحله‌ای `/loans/new` برای قرارداد، ذخیره اقساط، برنامه تخصیص و تنظیمات یادآور/بودجه زیان.
- مسیر `/loans/[id]` با Summary، Schedule، سرمایه و ذخیره، و سناریوهای بازده ثابت.
- مسیر `/loans/[id]/edit` برای تنظیمات عملیاتی بدون بازنویسی قرارداد پایه.
- Payment Dialog برای ثبت قسط واقعی از ذخیره، پول شخصی، فروش دارایی یا ترکیب آن‌ها.
- ساخت صندوق اختصاصی ذخیره در همان Transaction ساخت وام و ثبت `loan_reserve` به‌عنوان گردش سیستمی.
- اتصال صندوق موجود در V1 فقط برای صندوق خالی مجاز است تا موجودی قبلی به‌اشتباه سود وام محسوب نشود.
- اتصال صریح خرید و فروش سرمایه‌گذاری به وام از همان Transaction Dialog موجود.
- اتصال واریز شخصی به صندوق ذخیره به Loan برای جلوگیری از اشتباه گرفتن آورده شخصی با سود استراتژی.
- Dashboard card برای قسط نزدیک، کمترین Runway، مانده اصل و وضعیت هشدار.
- Global Search برای نام وام و وام‌دهنده.
- Activity Timeline برای پرداخت‌های واقعی وام.
- Reports card برای مانده بدهی، ذخیره، اقساط پرداخت‌شده در بازه و اثر خالص استراتژی.
- Offline shell برای `/loans` و `/loans/new` و Runtime cache برای مسیرهای Loan.

## قراردادهای اقتصادی حفظ‌شده

1. وام Income نیست و هیچ Loan flow به جدول `incomes` نوشته نمی‌شود.
2. ذخیره اولیه‌ای که از خود وام تامین شده `loan_reserve` است و آورده شخصی محسوب نمی‌شود.
3. واریز دستی‌ای که صریحاً به وام متصل شود آورده شخصی است و از اثر خالص استراتژی کسر می‌شود.
4. پرداخت شخصی قسط نیز جداگانه در `externalToman` ثبت و از عملکرد استراتژی کسر می‌شود.
5. وجه نقد قابل ردیابی وام در `StrategyAssets` باقی می‌ماند؛ خرید، فروش، هزینه اولیه و پرداخت از فروش آن را به‌صورت مشتق‌شده تغییر می‌دهند. اگر خریدهای متصل از وجه قابل ردیابی بیشتر شوند، کسری به‌صورت محافظه‌کارانه آورده شخصی محاسبه می‌شود.
6. فروش دارایی برای پرداخت قسط با `saleTransactionIds` ثبت می‌شود و فقط فروش متصل به همان وام پذیرفته می‌شود. انتخاب یک فروش، `loanId` آن تراکنش را به‌صورت پنهانی تغییر نمی‌دهد.
7. یک فروش نمی‌تواند برای دو قسط دوباره مصرف شود.
8. Stop-loss درصدی پیش‌فرض ساخته نمی‌شود. بودجه زیان با تعداد قسط تعریف می‌شود.
9. Scenario فقط سناریوی ثابت است و در UI صریحاً «پیش‌بینی بازار» معرفی نمی‌شود.

## طراحی و UX

جهت طراحی برای Fintech فارسی با اولویت اعتماد، خوانایی و تصمیم سریع تنظیم شد:

- RTL و mobile-first
- تراکم متوسط رو به بالا، بدون Card wall اضافی
- سه تصمیم فوری در Detail: قسط بعدی، ذخیره اقساط، مانده اصل
- رنگ سود و زیان فقط همراه متن و عدد، نه به‌عنوان تنها نشانه
- کنترل‌های اصلی با Touch target مناسب و Focus visible
- فرم‌ها با Label دائمی
- جدول اقساط در موبایل به Card تبدیل می‌شود
- سناریو و عملکرد واقعی در دو سطح بصری جدا نگه داشته می‌شوند

در محیط ساخت این Gateهای مستقل اجرا شدند:

- Full test suite: 298 تست Pass، صفر Fail. این مجموعه شامل تست‌های جدید Loan UI/analytics و تمام Regressionهای قبلی پروژه است.
- Syntax/Transpile check روی 389 فایل TypeScript و TSX: Pass.
- `node scripts/check-file-lines.mjs`: Pass، همه فایل‌های TypeScript حداکثر 250 خط.

به دلیل نبود دسترسی پایدار این محیط به npm registry، Dependency install کامل محلی در این محیط در دسترس نبود. بنابراین Gate نهایی `typecheck`, `lint`, full `npm test` و `build` باید پس از Replace روی ماشین توسعه اجرا شود.

Baseline قبل از Phase 3 بر اساس اجرای ماشین توسعه کاربر سبز بوده است: Typecheck، Lint، 290 تست، Regression و Production Build همگی Pass شده بودند.

## Gate ماشین توسعه

```bash
npm ci
npm run typecheck
npm run lint
npm test
npm run check:lines
npm run check:regressions
npm run build
```

اگر `node_modules` سالم و همگام با `package-lock.json` است، `npm ci` اختیاری است.
